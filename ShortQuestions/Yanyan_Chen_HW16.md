# Observability & Kubernetes – Answer Sheet

---

## Question 1: Three Pillars of Observability

The three pillars of observability are **metrics**, **logs**, and **traces**.

Metrics are numerical, time‑series data that represent the overall health and performance of a system, such as CPU usage, memory consumption, or request latency. They are mainly used for monitoring, alerting, and trend analysis.

Logs are discrete records of events that happened at a specific time, usually containing contextual information about what the system was doing. Logs are primarily used for debugging, auditing, and root‑cause analysis.

Traces represent the end‑to‑end journey of a single request as it travels through multiple services. Their main purpose is to help engineers understand request flow, identify bottlenecks, and debug latency or dependency issues in distributed systems.

---

## Question 2: Metrics Data Types

The four common metric types are **Counter**, **Gauge**, **Histogram**, and **Summary**.

A **Counter** is a monotonically increasing value that is used to count events, such as the total number of HTTP requests served.

A **Gauge** represents a value that can go up and down, such as current memory usage or the number of active connections.

A **Histogram** samples observations (like request latency) into configurable buckets and provides counts and sums. It is commonly used to understand latency distributions.

A **Summary** is similar to a histogram but calculates quantiles (for example, p95 or p99 latency) on the client side, making it useful for SLA‑focused latency tracking.

---

## Question 3: Structured Logging

Structured logging is a logging approach where logs are emitted in a machine‑readable format, such as JSON, with well‑defined fields like timestamp, log level, service name, request ID, and message.

It is preferred over unstructured (plain text) logging in production because it is easier to parse, search, filter, and analyze at scale. Structured logs integrate better with log aggregation and observability tools, enabling faster debugging and more reliable automated analysis.

---

## Question 4: Distributed Tracing Concepts

In distributed tracing, a **Trace** represents the complete lifecycle of a request across multiple services.

A **Span** is a single unit of work within a trace, such as an HTTP request or a database query. A trace is composed of multiple spans linked together in a parent‑child relationship.

**Context propagation** is the mechanism used to pass trace and span identifiers between services, usually via HTTP headers. This ensures that all spans generated by different services are correctly associated with the same trace.

---

## Question 5: Prometheus Pull Model

Prometheus uses a pull‑based model where it periodically scrapes metrics from HTTP endpoints exposed by applications or exporters.

The main advantages of the pull model are simplicity, better reliability, and easier service discovery. Prometheus can detect unhealthy targets automatically, and metrics collection does not depend on the application successfully pushing data.

The disadvantages include difficulty with short‑lived jobs and environments where targets cannot be reached directly. In such cases, a push model (or tools like Pushgateway) may be more suitable.

## Question 6: Control Plane Components

The four main Kubernetes control plane components are **kube‑apiserver**, **etcd**, **kube‑scheduler**, and **kube‑controller‑manager**.

The kube‑apiserver is the central entry point for all cluster operations and exposes the Kubernetes API.

etcd is a distributed key‑value store that persistently stores all cluster state and configuration.

The kube‑scheduler is responsible for assigning Pods to suitable nodes based on resource availability and constraints.

The kube‑controller‑manager runs control loops that ensure the actual cluster state matches the desired state, such as maintaining replica counts.

---

## Question 7: kubelet

kubelet is an agent that runs on every Kubernetes worker node. It is responsible for communicating with the kube‑apiserver, receiving Pod specifications, and ensuring that the containers defined in those Pods are running and healthy on the node.

---

## Question 8: etcd

etcd is a highly available, consistent key‑value store used by Kubernetes to store all cluster state, including configuration data, metadata, and scheduling information.

It is critical to the cluster’s operation because Kubernetes relies on etcd as the single source of truth. If etcd becomes unavailable or corrupted, the cluster cannot function correctly.

---

## Question 9: kube‑proxy

kube‑proxy is a network component that runs on each node and implements Kubernetes Service networking.

It maintains network rules (using iptables or IPVS) that route traffic from a Service’s virtual IP to the appropriate backend Pods, enabling load balancing and stable service discovery.

---

## Question 10: Scheduler

The Kubernetes Scheduler decides where to place a Pod by evaluating available nodes and selecting the most suitable one.

It considers factors such as CPU and memory availability, node affinity and anti‑affinity rules, taints and tolerations, resource requests, and scheduling policies. The scheduler first filters out unsuitable nodes and then scores the remaining ones to choose the best fit.
